# CI/CD and CLI releases

## Continuous integration

Pull requests to `dev` and `main`, pushes to those branches, and manual dispatch run Linux tests, build, structural QA, a LibreOffice PDF/PNG preview, Windows unit tests, CLI container smoke checks, CodeQL, secret scanning, and dependency review. The stable required status is `ci-gate`. Its success means automated checks passed; it does not claim Harness review, scientific verification, or human visual approval.

The CI and release presentation is generated from `examples/research-demo.json` and `sources/evidence.json`. All of its values are invented fixtures. Workflow artifacts contain only that synthetic PPTX, its QA and lineage reports, and its PDF/PNG preview, retained for 14 days.

## Versioned releases

Every PR merged to `main` must have exactly one of `release:patch`, `release:minor`, or `release:major`. The release workflow uses the highest existing `vMAJOR.MINOR.PATCH` tag as its version base. Until the first tag exists, it uses `0.1.0` as the seed, so a first patch release is `v0.1.1`. `package.json` remains private and is not used as a continuing version source; no npm package is published.

The workflow creates a GitHub Release with generated release notes, the synthetic sample deck and QA/lineage reports, PDF/PNG preview, and `SHA256SUMS`. The CLI image is published to `ghcr.io/georgeorange-crypto/aiautoslides-making` for `linux/amd64` and `linux/arm64`, tagged with the exact version, `major.minor`, and `latest`. BuildKit adds an image SBOM and provenance; release files receive GitHub build provenance attestations.

GitHub does not expose a supported REST setting for changing GHCR visibility. After the first image is published, open the package under the repository owner's **Packages** list and set **Package settings → Change visibility → Public**. The release job verifies anonymous pull access and both platform manifests before it creates the Git tag or Release. If the package is still private, the job stops with instructions; set it public and rerun that job. Later tags preserve and recheck the package's public visibility.

## Run the CLI image

The image runs the local CLI only. It does not start the REST API or MCP server and does not expose a network port. Mount a project directory to `/work`; pass paths inside that mount. On Linux, provide your host UID/GID so generated files are writable by your account:

```sh
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD:/work" -w /work \
  ghcr.io/georgeorange-crypto/aiautoslides-making:latest \
  validate --input examples/research-demo.json --evidence sources/evidence.json

mkdir -p outputs
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD:/work" -w /work \
  ghcr.io/georgeorange-crypto/aiautoslides-making:latest \
  build --input examples/research-demo.json --evidence sources/evidence.json --out outputs/demo.pptx
```

For Windows Docker Desktop, mount the current directory and use the same container paths; omit `--user` if the host does not provide compatible Linux UID/GID mapping. The container does not bundle LibreOffice, so PDF/PNG previews are generated by the CI/release runner or by a host installation.

## Branch protection and security

`main` and `dev` require pull requests and the `ci-gate` status, disallow force pushes and branch deletion, and do not require a minimum approval count. Release tags are created only from merged PRs to `main`. GitHub Actions use full commit SHA references. Dependabot checks npm, Actions, and Docker dependencies weekly.

Previously tracked bake-off evidence and generated artifacts remain in the repository's existing history; this CI change does not rewrite published history. `.gitattributes` excludes the tracked local output/artifact folders, generated demo previews, and template fixture from GitHub Release source archives. New CI uploads, Docker build contexts, and attached Release assets are explicitly scoped and exclude those materials.
