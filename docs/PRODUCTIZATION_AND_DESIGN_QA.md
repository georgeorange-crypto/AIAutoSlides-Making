# 产品化与设计能力问答

**整理日期：** 2026-11-12  
**范围：** 本文从阶段状态问答之后开始，汇总 App 产品化、AI 接入、内容设计判断、个性化和调研素材流程。阶段完成情况不在本文重复。  
**状态口径：** “已实现”依据当前代码和报告；“可行方案”是建议，不表示已经开发。

## Q1. 项目可以打包成 Windows 或 Android App 吗？

**答：当前仍未打包成 App。仓库已有 Windows 本地优先的 CLI、loopback REST API 和 stdio MCP 工作流，但没有图形界面、安装程序或 Android 客户端。**

当前项目是 Node.js 生成器，提供 CLI、单用户 loopback REST API、SQLite 项目/任务状态、可编辑 PPTX 构建、QA/预览工作流和 stdio MCP；仍没有图形界面、安装程序或移动端适配层。网络调研和可选模型调用不由本地默认工作流自动触发。

### Windows 路线

可以在现有本地生成核心外增加桌面 UI 和安装包。界面可负责选择源文件、编辑分镜、选择主题、展示审核意见、触发构建并打开 PPTX/PDF。现有 CLI 可继续承担生成任务。需要进一步处理依赖分发、路径和权限、日志、升级、PowerPoint/LibreOffice/Poppler 是否随应用提供，以及用户数据保存位置。

### Android 路线

不能把当前 Windows/Node 命令直接打包后就认为可用。需要重新处理本地文件访问、PPTX 生成运行时、PDF 预览和字体/图表呈现。可以评估纯本地移动端实现，或由 App 调用受保护的服务端；若用户需要离线和研究材料不出设备，需优先设计本地方案并验证 Android 运行时兼容性。

参考：`package.json`、`src/cli.mjs`、`src/render.mjs`、`scripts/preview.mjs`、`docs/CONFIGURATION.md`。本项目还没有作出 Electron、Tauri、Capacitor 或其他框架的正式选型。

## Q2. 做成 App 后，Codex 或其他 AI 如何使用？

**答：App 界面与 AI 工具接口是两件事；当前已有受限的本地 REST API 和 stdio MCP，但还没有桌面 UI 或远程认证服务。**

Codex 可以把项目当作代码工作区，按 `AGENTS.md` 和 npm 命令操作。可选 OpenAI 分镜功能会调用 Responses API。外部 Agent 还可通过 loopback REST 或 stdio MCP 调用本地项目、来源、分镜编辑、计划、Critic、渲染任务、状态和产物元数据；MCP 依赖单独运行的本地 API。该 API 单用户、单进程、未认证，不可暴露到网络。项目 Skill 已存在，但这不等同于远程服务或多 Agent 调度器。

### 建议的工具层

优先将本地 CLI 的受支持操作包装成受限的 MCP 工具，逐步开放：

1. 列出用户明确选定的工作目录中的素材。
2. 导入本地 PDF/DOCX 文本并返回页/段落定位与证据记录。
3. 校验分镜并生成 Critic 报告。
4. 生成或更新分镜草稿，清楚标记 AI 草稿状态。
5. 在人工审核通过后构建 PPTX，并返回输出路径和 QA 报告。
6. 在可用环境中生成 PDF/PNG 预览。

Windows App、未来 Android App 和 Agent 工具应尽量调用同一生成核心，避免分别实现两套 PPT 逻辑。接口应限制可访问目录、允许的文件类型和输出位置；研究材料需明确是否允许发往外部 API。

HTTP API 可作为远程服务或多客户端场景的另一种选择，但需要认证、文件隔离和数据留存策略。MCP/HTTP 都是后续架构建议，不是当前已有功能。

## Q3. 内容组织、重点取舍、表达形式、审美和时间控制目前怎么做？

**答：项目已提供内容规划和规则化审稿的基础，但不能完全自主决定讲什么、删什么、重点讲多深或用哪种视觉形式。**

### 当前已实现的辅助能力

- 可选 AI 分镜接受受众类型、演讲目标和时长，按受约束的结构起草 6–9 页内容；提示要求使用材料中的事实、标注假设、保留限制，不能自行创造图表数值。
- 三种受众类型已进入 AI 规划接口：`research_group`、`academic_conference`、`investment_committee`。
- Slide Critic 会检查受众/目标/时长是否缺失，以及部分类型化的内容提醒。例如，研究组演示可能缺少方法、限制或下一步；投资委员会演示可能缺少风险或决策请求。
- 对事实页可登记 `claim_support`，记录逐条主张、来源摘录、定位和人工审核状态。缺失、待审核或被标记为矛盾的记录会产生对应提示或错误。
- 支持若干既定页面布局、原生数据图表、图表文字描述、主题预览和人工确认主题。用户可在分镜中选择版式、补充讲者备注。
- 如果把完整讲稿写入备注，并提供语速和时间窗，Critic 可以估算讲稿时长并提示是否超出给定范围。

### 当前限制

- AI 规划器起草故事线，但没有可靠的内容价值模型来判断材料中哪些内容应该舍弃、哪些发现最重要，或每条主张应讲多细。它的输出仍是草稿。
- Critic 使用可解释规则和文本检测；它不能真正理解所有论据关系，也不能替代领域专家判断“这个结果值得讲吗”。数字字面匹配检查不能证明数字语义正确。
- 目前没有通用的媒介选择器，不能可靠判断某段内容应改成照片、系统图、表格、数据图还是文字。图表需要按受支持的数据结构提供；复杂图片/架构视觉还需另行准备。
- 版式规则与主题能帮助保持一致性，但不能完整评估审美、叙事节奏、现场互动或目标会议的具体要求。时间估算依赖用户提供的讲稿和语速，不是语音识别或实际彩排。
- 所有 AI 草稿需经过人工审核；批准与内容哈希绑定，草稿之后被修改就要重新审核。

参考：`src/ai-plan.mjs`、`src/critic.mjs`、`src/critique.mjs`、`src/review-draft.mjs`、`docs/M3_IMPLEMENTATION_REPORT.md`、`docs/SCHEMA.md`。

## Q4. 有个性化目录、用户偏好和多角度选择题向导吗？

**答：有少量可配置字段和主题确认；没有完整的个性化访谈向导或持久化用户档案。**

### 目前可以提供的定制

- 规划时通过参数指定受众类型、目标和演讲时长。
- 在分镜中指定主题、页面类型、版式、正文、证据 ID 和讲者备注。
- 使用主题预览流程比较三个内置主题，由用户确认后记录项目级设计说明和 tokens。当前确认的项目默认主题为 `keynote-minimal`。

### 尚未实现的定制

- 没有用户级偏好目录/Profile，例如为不同用户长期保存语言、正式程度、字号、配色、密度、叙事习惯和禁用风格。
- 没有从多个维度逐步提问的 UI 向导；还不能通过多选题和补充问题自动产出个性化设计档案。
- 没有根据用户评分、改稿和满意度反馈持续学习。用户选择的主题只记录为显式确认，不等于系统已经学会审美偏好。

后续可将个人设置和单次演示参数分开保存，提供“听众与目的、专业程度、语言、时长、演讲场景、视觉风格、信息密度、图表偏好、素材权利”等问题，并允许用户逐项跳过、补充、预览和修改。最终满意度仍需由用户确认，不能由自动评分代替。

参考：`src/ai-plan.mjs`、`src/theme-gallery.mjs`、`src/select-design.mjs`、`docs/design.md`、`docs/design-tokens.json`。

## Q5. 项目支持主动调研、下载素材、保存归类并分析如何使用吗？

**答：当前提供 opt-in 的有限调研/素材工作流及本地 PDF/DOCX 抽取；它们不会自动核验科学事实或素材授权。**

### 当前已有

- 使用 OpenAlex/Crossref/arXiv 查询元数据；可选单页 Crawl4AI 抓取、用户选定的 arXiv PDF 下载和单张 Wikimedia Commons 图片检索/下载。网络操作需要显式命令开关；抓取不遍历链接、不批量下载。
- 从本地 PDF/DOCX 提取文字与定位；支持离线 PDF OCR、DOCX 图像提取和 PDF 图像 XObject 提取。
- 为导入材料记录源文件哈希、抽取文本哈希，并生成 `verified:false` 的证据台账记录。抽取不等于事实核验，生成的材料仍需人工核对。
- 证据记录可存来源、定位、核验状态和人工备注；分镜通过 `evidence_ids` 引用证据。

### 当前没有

- 基于私有研究材料自动发起外部搜索或付费模型调用；这些行为需要单独授权并保持可见。
- 批量媒体下载、自动许可批准，以及对所有 PDF 内嵌图像类型的完整提取。
- 图片、音频、视频的统一导入、转录、标签、授权记录和本地素材库。
- 自动判断材料支持哪项主张、适合哪一页或应采用图片/图表/表格/文字。
- 自动写入带出处与许可元数据的素材使用建议。

### 建议的未来研究链路

```text
用户研究问题
  → 搜索并记录候选来源
  → 保存本地副本或引用信息、许可与日期
  → 提取段落/页面/媒体元数据
  → 将证据映射到候选主张并标注置信与缺口
  → 给出素材用途建议（支持哪页、适合何种呈现、限制是什么）
  → 人工核验后进入分镜和 PPTX
```

设计时需要把“发现材料”“抽取内容”“判断其是否支持主张”“建议如何使用”分开记录。搜索结果和用户文件均为待审材料，不能自动视为可信证据或 Agent 指令。若接入外部搜索或 AI 服务，还要对私密材料上传和费用设置明确开关。

参考：`src/import-document.mjs`、`docs/M4_IMPLEMENTATION_REPORT.md`、`src/validate.mjs`、`src/cli.mjs`、`sources/evidence.json`、`docs/SCHEMA.md`。

## 综合结论

当前产品的核心是**本地优先、来源可追溯、生成可编辑 PPTX 的工程工作流**。除受众参数、AI 分镜草稿、规则化内容审阅和人工审批门外，当前已有单用户本地 REST/MCP、有限 opt-in 研究/素材路径，以及确定性 audience-aware 内容规划和渲染文字 OCR 屏查；仍未形成 Windows App/安装包、远程多用户服务、完整持久化偏好、自动事实/许可判断或通用多媒体编排系统。

合理的产品化顺序是：先统一生成核心与受限 Agent 工具接口；再做本地素材清单和个性化向导；之后增加经授权的网页调研与素材分析；最后才依据真实使用反馈迭代自动内容取舍、媒介选择和移动端能力。每一步都应保留来源、人工审核和可复现输出。
